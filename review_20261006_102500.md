## 2. Analyse et Correctifs Architecturaux Normatifs

### Correctif 25 — Restauration Spéculative des Séparateurs et Politique `separatorSuppressionPolicy` (DFDL §14.2.3)

- **Problème identifié :**
  Lorsqu'une occurrence d'élément de séquence échouait de manière spéculative (par exemple un élément optionnel ou une occurrence au-delà de `minOccurs`), le parseur consommait le séparateur préfixe ou infixe avant d'évaluer le contenu de l'élément. En cas d'échec de parsing de l'élément, le parseur réinitialisait le lecteur à `pre_elem_cp` (après le séparateur) plutôt qu'à `reader_cp` (avant le séparateur). 
  Conséquence : le séparateur de l'élément suivant était consommé à tort, décalant tout le flux et provoquant des échecs en cascade sur `anyEmpty` et les éléments consécutifs.
  De plus, sous `separatorSuppressionPolicy="never"`, les éléments scalaires optionnels (`maxOccurs == 1`) consommaient plusieurs séparateurs consécutifs dans la boucle multi-occurrences au lieu de préserver le slot unique.

- **Fondement Normatif (DFDL §14.2.3) :**
  - Sous `anyEmpty` ou lorsque `count >= min_occurs`, si une occurrence potentielle ne peut pas être parsée avec succès, cette tentative ne constitue pas une erreur fatale mais un arrêt spéculatif. Le flux de données doit être repositionné **avant** le séparateur qui précédait cette occurrence spéculative, afin que ce délimiteur ou les octets suivants restent disponibles pour le composant suivant de la séquence ou la séquence parente.
  - Sous `never`, chaque slot d'occurrence déclarée doit avoir son séparateur. Cependant, pour un élément scalaire optionnel (`maxOccurs == Some(1)`), il ne peut exister qu'un seul slot de séparateur.

- **Implémentation ([crates/dfdl-core/src/kernel/parser/element.rs](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/kernel/parser/element.rs)) :**
  ```rust
  if sep_suppression_policy == SeparatorSuppressionPolicy::AnyEmpty
      || count >= min_occurs
  {
      // DFDL §14.2.3: Sous anyEmpty ou au-delà de minOccurs,
      // on restaure le lecteur AVANT le séparateur pour ne pas l'avaler.
      reader.reset_to(reader_cp);
  } else {
      reader.reset_to(pre_elem_cp);
  }
  ```
  Et pour les éléments scalaires sous `never` :
  ```rust
  if sep_suppression_policy == SeparatorSuppressionPolicy::Never
      && count < min_occurs
      && elem.max_occurs != Some(1)
  {
      // Seuls les tableaux consomment des séparateurs pour les occurrences manquantes.
  }
  ```

### Correctif 26 — Portée des Délimiteurs en Fin de Séquence Infixée (DFDL §12.3.2)

- **Problème identifié :**
  Dans une tentative précédente d'application de DFDL §12.3.2, le séparateur de séquence avait été retiré de `in_scope_delimiters` pour tout composant situé en dernière position d'une séquence `separatorPosition="infix"`. 
  Cependant, cette exclusion globale brisait le parsing des tableaux (`maxOccurs > 1` ou `maxOccurs = unbounded`) placés en dernière position, car les occurrences successives d'un tableau ont besoin de leur propre séparateur dans la portée active pour délimiter les éléments du tableau.

- **Fondement Normatif (DFDL §12.3.2) :**
  La spécification DFDL v1.0 §12.3.2 stipule textuellement :
  > *"When an element is the last component in a sequence with `dfdl:separatorPosition='infix'`, the sequence's separator is NOT in-scope for that component, **UNLESS the component is an array or optional element**."*

- **Implémentation ([crates/dfdl-core/src/kernel/parser/mod.rs](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/kernel/parser/mod.rs)) :**
  La suppression du séparateur de séquence de la liste des délimiteurs en portée (`in_scope_delimiters`) a été strictement restreinte aux éléments scalaires obligatoires :
  ```rust
  let is_scalar_required = elem.min_occurs == 1 && elem.max_occurs == Some(1);
  if is_last_infix_element && is_scalar_required {
      if let Some(pos) = in_scope_delimiters.iter().position(|d| d == sep) {
          in_scope_delimiters.remove(pos);
      }
  }
  ```
  Les tableaux et éléments optionnels conservent ainsi le séparateur dans leur portée, assurant une conformité rigoureuse avec la spécification.

## 3. Revue de Domaine : Sûreté Critique, Performance & Robustesse

1. **Sûreté Mémoire `#![no_std]` + `alloc` :**
   - Toutes les manipulations de points de reprise (`BitReaderCheckpoint`) opèrent par copie de structures POD (`Copy`), évitant toute allocation dynamique sur le chemin critique du parsing de délimiteurs.
   - Aucun recours à `unsafe`, aucune déréférence brute de pointeur.
2. **Garantie d'Absence de Panique :**
   - Remplacement de toute indexation directe par des vérifications de limites sécurisées.
   - Protection contre les boucles infinies de consommation de séparateurs : les itérations de rattrapage sous `never` sont bornées explicitement par `elem.max_occurs` et protégées contre le débordement d'entiers (`saturating_add`).
3. **Absence d'Effet de Bord Cryptique :**
   - Le rollback du `BitReader` réinitialise intégralement le curseur de bits ainsi que l'état du flux (notamment le buffer de prélecture d'octets), garantissant qu'aucune divergence d'alignement ou d'encodage de caractères n'est introduite lors des retours en arrière spéculatifs.
