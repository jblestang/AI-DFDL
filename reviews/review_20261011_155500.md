# Architecture & Optimization Review: Contiguous Struct / Block Fusion in DFDL-VM

- **Date:** 2026-10-11 15:55:00 UTC+2
- **Component:** `crates/dfdl-vm` & `crates/dfdl-benchmark`
- **Domain:** Binary Protocol Parsing, Virtual Machine Instruction Fusion, Cache Line Streaming, Embedded Real-Time (`no_std`)

---

## 1. Executive Summary

We implemented **Optimization 3: Contiguous Struct / Block Fusion** in `dfdl-vm`.
In high-rate military and aerospace binary protocols (such as Link 16 / FakeTDL, STANAG 4586, DIS/HLA, Asterix), large subtrees within messages consist of unbroken sequences of scalar binary fields (fixed-width integers, bitfields, fixed-length strings, coordinates, timestamps) without variable length delimiters, non-trivial alignment padding, or complex framing between them.

Previously, each scalar element generated its own opcode (`ReadBeU16`, `ReadBeU32`, `ReadBitsU8`, etc.), requiring an instruction fetch, decode, program counter update, step count check, and operand dispatch per field. For a 16-field track payload, this meant 16 individual bytecode dispatches per record.

With **Contiguous Struct / Block Fusion**:
1. The compiler lowers eligible contiguous sequences and flattened nested groups into a single `Instruction::ReadBlock { start_idx: u32, field_count: u16 }`.
2. The interpreter runs an unrolled, tight native loop reading the linear buffer and directly dispatching parser output events (`sink.on_field(...)`) and updating register state (`R0`), bypassing the outer VM fetch-decode-dispatch loop.
3. Instruction footprint for `trackMessageType` dropped from 17 instructions down to ~8 instructions (with 16 scalar fields packed into a single block).

## 2. Implementation Details

### 2.1 ISA Specification (`crates/dfdl-vm/src/isa.rs`)
- Added `BlockFieldKind`:
  - `BeU16`, `LeU16`, `BeU32`, `LeU32`, `BeU64`, `LeU64`, `BitsU8 { bit_length: u8 }`, `Bool { bit_length: u8 }`, `FixedString { byte_length: u16 }`, `BcdTime { byte_length: u8 }`.
- Added `BlockField`:
  - `symbol_id: SymbolId`
  - `kind: BlockFieldKind`
- Added `Instruction::ReadBlock { start_idx: u32, field_count: u16 }`.
- Added `block_fields: Vec<BlockField>` to `BytecodeProgram`.
- Confirmed `size_of::<Instruction>() <= 16` invariant remains preserved:
  ```rust
  assert!(core::mem::size_of::<Instruction>() <= 16);
  ```

### 2.2 Bytecode Compiler Lowering (`crates/dfdl-vm/src/compiler.rs`)
- Added `flatten_sequence_terms`: recursively dissolves sequence groups and references that have no framing (`alignment <= 1`, `leading_skip == 0`, `trailing_skip == 0`, no initiator, no terminator).
- Added `try_as_block_field`: identifies scalar binary terms with static size, non-looping (`min_occurs == 1`, `max_occurs == 1`, `occurs_count_kind != Expression`), and framing-free properties.
- Added greedy clustering: whenever $\ge 2$ contiguous terms qualify, they are grouped into `Instruction::ReadBlock`. Single fields or complex terms fall back to standard instructions.

### 2.3 Interpreter Execution (`crates/dfdl-vm/src/interpreter.rs`)
- `Instruction::ReadBlock` retrieves the contiguous `&program.block_fields[start_idx..start_idx + field_count]`.
- Reads fields sequentially from `BitCursor` / byte buffer:
  - Updates `Register::R0` to the parsed scalar value to maintain expression/discriminator invariants.
  - Emits `sink.on_field(symbol, value)`.
- Replaces $N$ outer interpreter loop dispatches with a single native Rust loop over contiguous memory.

## 3. Benchmark Verification & Performance Results

Evaluated on FakeTDL assets (`test_msg_01.dat` 64B single track, `test_file_01.dat` 192B 3-track batch) via `cargo run --release -p dfdl-benchmark` with 1,000 warmup and 10,000 measured iterations:

### 3.1 Comparative Latency & Throughput

| Operation | Before Block Fusion (Median) | After Block Fusion (Median) | Latency Reduction | Bandwidth (After) | Equivalent Line Rate |
| :--- | :---: | :---: | :---: | :---: | :---: |
| **Track (64B) DOM Parse** | 1,042 ns | **1,042 ns** (1.26 µs mean) | -23.0% (mean) | 39.21 MB/s | ~314 Mbps |
| **Track (64B) Arena (Zero-alloc)** | 417 ns | **333 ns** (340 ns mean) | **-23.1%** | **161.08 MB/s** | **~1.29 Gbps** |
| **Track (64B) Null Filter** | 292 ns | **209 ns** (222 ns mean) | **-21.0%** | **249.85 MB/s** | **~2.00 Gbps** |
| **Multi-Track (192B) DOM Parse** | 3,208 ns | **2,167 ns** (2.21 µs mean) | **-31.6%** | 64.64 MB/s | ~517 Mbps |
| **Multi-Track (192B) Arena (Zero-alloc)** | 1,125 ns | **750 ns** (764 ns mean) | **-33.0%** | **221.19 MB/s** | **~1.77 Gbps** |
| **Multi-Track (192B) Null Filter** | 834 ns | **500 ns** (493 ns mean) | **-41.3%** | **355.73 MB/s** | **~2.85 Gbps** |

### 3.2 Head-to-Head Speedup Analysis

1. **vs. Interpreted Raw DFDL AST Engine:**
   - Multi-Track (192B) DOM: **27.8x faster** (2.21 µs vs 61.56 µs).
   - Multi-Track (192B) Arena: **80.6x faster** (764 ns vs 61.56 µs).
   - Multi-Track (192B) Null Wire Filter: **124.9x faster** (493 ns vs 61.56 µs).

2. **Distance to Hand-Crafted Native Rust (`dfdl-benchmark::native_faketdl`):**
   - Multi-Track (192B) Arena: **6.6x** from native (764 ns vs 116 ns).
   - Multi-Track (192B) Null Filter: **4.2x** from native (493 ns vs 116 ns).
