## 2. Changes Summary & Root Cause Analysis

### A. Prefixed/Explicit Complex Element Enclosing Lengths in Expressions (`dfdl:contentLength`)
- **Root Cause**: When calculating `dfdl:contentLength(.., "bytes")` inside an element contained in a complex element with `dfdl:lengthKind="prefixed"` or `"explicit"`, the parent complex element's length is known from its prefix length or explicit length property, but was not tracked in `ExprContext`. Furthermore, for `LengthUnits::Characters`, the bit length must be computed using the character unit width of the element's encoding (e.g., 16 bits for UTF-16BE), rather than assuming 8 bits per character.
- **Specification Reference**: DFDL §12.3.4 (dfdl:lengthKind "prefixed") & §13.7 / §23.5.1 (dfdl:contentLength).
- **Implementation**:
  - Added `enclosing_complex_elements: Vec<(String, usize, LengthUnits, String)>` to `ParserEngine`.
  - In `parse_complex_element`, pushed `(elem_name, length, length_units, encoding)` upon evaluating complex element length, and popped it after children finish parsing.
  - In `ExprContext`, added `with_enclosing_lengths(&self.enclosing_complex_elements)` across parser dispatch points.
  - In `eval_expr`, resolved `dfdl:contentLength` against `ctx.enclosing_lengths`, scaling character lengths with `crate::encoding::encoding_unit_bits(encoding)`.
  - In `parse_complex_element`, set and restored `reader.bit_limit()` using `encoding_unit_bits` so unbounded children stop at the complex element boundary.
- **Impact**: Resolved `pl_complexContentLengthBytes_1`, `pl_complexValueLengthBytes_1`, `pl_complexContentLengthBits_1`, `pl_complexValueLengthBits_1`, `pl_complex_bin_bytes`, `pl_complex_bin_bits`, and `pl_complexContentLengthCharacters_1`.

### B. Schema Validation for Variable-Width Encoding with Prefixed Length on Complex Elements
- **Root Cause**: DFDL schemas that declare complex elements with `dfdl:lengthKind="prefixed"` and `dfdl:lengthUnits="characters"` using variable-width encodings (such as UTF-8) cannot unparse or determine prefix length deterministically and must be rejected with a Schema Definition Error.
- **Specification Reference**: DFDL §12.3.4 & Daffodil Conformance Rule.
- **Implementation**:
  - Implemented `dfdl_core::encoding::is_variable_width_encoding(encoding)` in [encoding.rs](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/encoding.rs).
  - In [compiler.rs](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-schema/src/compiler.rs), added validation rejecting complex elements with `LengthKind::Prefixed`, `LengthUnits::Characters`, and variable-width encoding with a Schema Definition Error.
- **Impact**: Resolved `pl_complexContentLengthCharacters_utf8_1`.

### C. Literal Number Formatting Properties Incorrectly Treated as Expressions (`testExpressionPropertyWarnings`)
- **Root Cause**: DFDL 1.0 §13.7.1 Table 46 stipulates that properties `textStandardInfinityRep`, `textStandardNaNRep`, and `textStandardZeroRep` cannot be DFDL expressions; they are literal strings. In [element.rs](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/kernel/parser/element.rs), values enclosed in `{...}` were erroneously being dispatched to `evaluate_property_str_at`, causing failure on literal representations like `"{../ex:thisCantBeAnExpression}"`.
- **Implementation**: Removed dynamic expression evaluation for these non-expression numeric representation properties in `element.rs`.
- **Impact**: Resolved `expressionPropertyWarning1`.

### D. Element Context Path for `occursCount` Expression Evaluation (`NVI_with_CDK1`)
- **Root Cause**: When evaluating `dfdl:occursCount` expression for an array element, `builder.current_path()` points to the parent element (because `StartElement` has not yet occurred for the array). Relative paths like `{ ../ex:count }` expect to navigate from the array element itself to its parent and find sibling elements.
- **Implementation**: In [element.rs](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/kernel/parser/element.rs), pushed the target element's local name to `current_path` before creating `ExprContext`, matching the pattern used in assert, discriminator, and length evaluations.
- **Impact**: Resolved `NVI_with_CDK1`.
