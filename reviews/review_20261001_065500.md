## 1. Domain Expertise Analysis

### 1.1 DFDL Standard & Framing Semantics (DFDL 1.0 §12.1 & §12.3)
- **Component Framing Order & Skip Properties:**
  - *Standard Requirement (DFDL 1.0 §12.1 & §12.3):* Framing for an element or group component specifies bitstream alignment and skip regions around the payload:
    - **Left framing:** `dfdl:leadingSkip` (in `dfdl:alignmentUnits`), followed by `alignment`, followed by `initiator`.
    - **Payload:** Element or group content.
    - **Right framing:** `terminator`, followed by `dfdl:trailingSkip` (in `dfdl:alignmentUnits`).
    - For sequence elements with separators, each occurrence has its own framing, with prefix/infix separators preceding left framing, and postfix separators following right framing.
  - *Root Cause Discovered:* Neither `dfdl:leadingSkip` nor `dfdl:trailingSkip` were parsed or resolved into `ResolvedProperties` in `dfdl-schema`/`dfdl-core`. Consequently, schemas with skips (e.g. `BinaryInput_01.tdml`, `Aligned_Data.tdml`) failed to skip leading/trailing padding bits or bytes. This shifted the bitstream alignment for all subsequent elements, causing:
    1. Unconsumed trailing bytes remaining at EOF (`"Left over data remaining after root element parse"`).
    2. Bit-level misalignment of payload bits, corrupting ASCII characters (e.g., bit-shifted '4' resulting in `"Parsed value ?42 out of range for xs:long"`).
  - *Fix Applied:*
    1. Added `leading_skip: usize` and `trailing_skip: usize` fields to [`ResolvedProperties`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/schema/ir.rs#L224).
    2. Implemented resolution of `leadingSkip` and `trailingSkip` in [`to_resolved_properties`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/expr/properties.rs#L630).
    3. Integrated left framing (`leadingSkip` $\to$ `alignment` $\to$ `initiator`) and right framing (`terminator` $\to$ `trailingSkip`) into both [`parse_term_internal`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/kernel/parser.rs#L694) (for group/sequence/choice terms) and [`parse_element_with_separators`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/kernel/parser.rs#L1430) (for each element occurrence).
    4. Added matching unparsing support in [`unparser.rs`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/kernel/unparser.rs#L79) using `fill_byte`.

### 1.2 Textual Integer Number Representation & Radix (DFDL 1.0 §13.6)
- **Arbitrary Radix Parsing with `dfdl:textStandardBase`:**
  - *Standard Requirement (DFDL 1.0 §13.6):* The property `dfdl:textStandardBase` specifies the number base of the text representation (values: 2, 8, 10, 16; default: 10). It applies to standard integer types (`xs:byte`, `xs:short`, `xs:int`, `xs:long`, and unsigned variants).
  - *Root Cause Discovered:* The parser hardcoded text number parsing to decimal (`base 10`). In `TextStandardBase.tdml` and `TextNumberProps.tdml`, binary strings (`11111111...`), octal strings (`177777...`), and hexadecimal strings (`7fffffffffffffff`, `7f`) were parsed as base 10, causing integer overflow errors (`Parsed value 7fffffffffffffff out of range for xs:long`).
  - *Fix Applied:* Added `text_standard_base: u32` to [`ResolvedProperties`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/schema/ir.rs#L286), resolved it in `to_resolved_properties`, and updated [`parse_text_number`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/kernel/parser.rs#L2810) to parse text integers using `i64::from_str_radix` and `u64::from_str_radix` with sign preservation when `base != 10`.

### 1.3 XPath 2.0 Arithmetic & Expression Coercion (DFDL 1.0 §23.2 & W3C XPath 2.0 §3.4)
- **Numeric Coercion, `div` vs `idiv`, and Decimal Coercion:**
  - *Standard Requirement (XPath 2.0 §3.4 & §6.2.4):*
    - The `div` operator performs numeric division (returning `xs:decimal` or `xs:double`). Division of integers produces float/double (`5 div 2 = 2.5`).
    - The `idiv` operator performs integer division (truncating towards zero). Division by zero in `idiv` or when either operand is `NaN`/`INF` is an error (`FOAR0001`/`FOAR0002`).
    - Operands of type `xs:decimal` participate in arithmetic operations identically to other numeric types.
  - *Root Cause Discovered:*
    1. In `crates/dfdl-core/src/expr/eval.rs`, `coerce_numeric` did not match `DfdlValue::Decimal(s)`. Any expression involving `xs:decimal` literals or elements fell through to `Type mismatch in division` (4 failures) or `Type mismatch in modulo` (3 failures).
    2. `BinaryOp::Div` and `BinaryOp::IDiv` were handled identically and performed integer division for integer inputs, failing expressions like `5 div 2` expecting `2.5`.
    3. `eval_mod` lacked support for `Double` and mixed numeric operands.
  - *Fix Applied:*
    1. Updated `coerce_numeric` to parse `DfdlValue::Decimal` as `Long` or `Double`.
    2. Separated `BinaryOp::Div` from `BinaryOp::IDiv`: `eval_div` returns `Double(a as f64 / b as f64)` on fractional results, while `eval_idiv` truncates towards zero with checked integer arithmetic.
    3. Added `Double` and mixed-operand support to `eval_mod` using checked division/remainder and IEEE float modulo.
    4. Enhanced `convert_value_to_simple_type` in `parser.rs` to support bidirectional conversions between `Decimal`, `Double`, and integer types.

### 1.4 Embedded Systems & Memory Safety (`#![no_std]` + `alloc`)
- **Strict Lint Compliance & Safe Arithmetic:**
  - All integer division and modulo calculations in `eval_div` and `eval_idiv` employ `checked_rem` and `checked_div`, preventing arithmetic overflow panics (`-D clippy::arithmetic-side-effects`) on edge cases like `i64::MIN / -1`.
  - Zero compiler warnings, zero clippy warnings (`cargo clippy --all-targets -- -D warnings`).
  - Formatted cleanly with `cargo fmt --check`.
  - Verified 100% `#![no_std]` compatibility on embedded target `thumbv7m-none-eabi`.
