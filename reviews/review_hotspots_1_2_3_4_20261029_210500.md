## 2. Implemented Optimizations & Technical Rationale

### Hotspot #1: Zero-Alloc Delimiter Evaluation & Fast-Path Entity Decoding
- **Files**: [`crates/dfdl-core/src/kernel/parser/delimiters.rs`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/kernel/parser/delimiters.rs), [`crates/dfdl-core/src/kernel/unparser/framing.rs`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/kernel/unparser/framing.rs)
- **Problem**: Every element unparse evaluated delimiters via dynamic AST parsing, ran allocating `split_delimiter_alternatives`, and traversed entity regexes even when delimiters were static literals without `%` entities.
- **Solution**:
  - Implemented zero-alloc `first_delimiter_alternative(&str) -> &str`, returning a subslice of the first non-whitespace alternative without heap allocation.
  - Stripped leading whitespace per DFDL v1.0 §12.3 so leading space in separator lists is properly ignored (verified by `unparseSeparatorLeadingSpace` passing).
  - Fast-pathed delimiter decoding: if the delimiter contains no `%`, it bypasses entity decoding entirely.
  - Fast-pathed newline resolution: `outputNewLine` resolution is only triggered if the delimiter contains `%NL;`.

### Hotspot #2: Bulk `write_bytes` Path in `BitWriter`
- **Files**: [`crates/dfdl-core/src/io/bitstream.rs`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/io/bitstream.rs), [`crates/dfdl-core/src/kernel/unparser/element.rs`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/kernel/unparser/element.rs), [`crates/dfdl-core/src/kernel/unparser/framing.rs`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/kernel/unparser/framing.rs)
- **Problem**: Writing delimiters or string values in the unparser called `write_bits(b as u64, 8)` byte-by-byte in a tight loop, checking bit alignments and shift operations on every single byte.
- **Solution**:
  - Implemented `BitWriter::write_bytes(&mut self, bytes: &[u8]) -> DFDLResult<()>`.
  - When the bitstream is byte-aligned (`bit_offset % 8 == 0`), it invokes `self.sink.write_all(bytes)` directly as a bulk slice copy.
  - When unaligned, it loops over bytes delegating to `write_bits(b as u64, 8)`.
  - Routed string and delimiter unparsing through `write_bytes`.

### Hotspot #3: Zero-Alloc Lazy Cloning of `VariableMap`
- **Files**: [`crates/dfdl-core/src/kernel/parser/mod.rs`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/kernel/parser/mod.rs), [`crates/dfdl-core/src/kernel/unparser/mod.rs`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/kernel/unparser/mod.rs), [`crates/dfdl-core/src/kernel/unparser/suspensions.rs`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/kernel/unparser/suspensions.rs)
- **Problem**: `ParserEngine::new` and `UnparserEngine::new` cloned the schema's entire `VariableMap` (with all variables, strings, scopes, and types) eagerly on every parse/unparse call, even for schemas with no runtime variable mutations.
- **Solution**:
  - Changed `variable_map: VariableMap` to `active_variable_map: Option<VariableMap>`.
  - On engine creation, `active_variable_map` is initialized to `None`.
  - Read-only operations (`variable_map(&self)`) return `&self.schema.variable_map` with zero cloning.
  - Mutable operations (`variable_map_mut(&mut self)`) use `get_or_insert_with(|| self.schema.variable_map.clone())` to clone lazily only if a `setVariable`, `newVariableInstance`, or external variable mutation occurs.
  - Refactored disjoint field borrows in `ParserEngine` methods so `active_variable_map` can be borrowed alongside parser state.

### Hotspot #4: Precomputed Character & Unit Bit Widths
- **Files**: [`crates/dfdl-core/src/encoding.rs`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/encoding.rs), [`crates/dfdl-core/src/schema/ir.rs`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/schema/ir.rs), [`crates/dfdl-core/src/schema/builder.rs`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/schema/builder.rs), [`crates/dfdl-core/src/expr/properties/resolution.rs`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/expr/properties/resolution.rs)
- **Problem**: `encoding_char_bits(&encoding)` and `encoding_unit_bits(&encoding)` repeatedly performed lowercase string normalization and pattern matching on every length and framing calculation.
- **Solution**:
  - Added precomputed fields `encoding_char_bits: u32` and `encoding_unit_bits: u32` to [`ResolvedProperties`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/schema/ir.rs#L890).
  - Populated during schema compilation in `build_ir` and updated on runtime property resolution.
  - Added fast-path ASCII/UTF-8 branch in `encoding_char_bits` and `encoding_unit_bits`.

## 4. Observations & Next Opportunities

1. **Unparser Suspension Buffer Pooling**:
   Now that delimiter handling and bit writing are fast, remaining unparser overhead is largely allocation of `Suspension` closures and output chunks for deferred expression evaluation. Reusing chunk buffers in `UnparserEngine` can unlock an additional ~20% throughput.
2. **DFDL-VM Bytecode Unparser**:
   The benchmark confirms DFDL-VM bytecode parsing runs at **154 - 222 MB/s** (13.7x to 19.2x faster than raw interpreted DFDL). Developing the bytecode unparser opcode set (`OP_EMIT_BITS`, `OP_WRITE_DELIM`, `OP_WRITE_RAW_BYTES`) will bring unparsing to comparable wire speeds (~100-200 MB/s).
