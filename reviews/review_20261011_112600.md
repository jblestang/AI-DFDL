## 2. Updated Breakdown: Why Parse Was 4× Slower, and Why It Is Now 2×

### The 46% Latency Reduction Explained

1. **Elimination of Speculative Lookahead Allocations:**
   - Previously, every message boundary check inside the file array executed:
     ```rust
     for _ in 0..1024 { ... read_bits(8) ... }
     ```
     This allocated a fresh `Vec<u8>`, copied up to 1,024 bytes, converted them to UTF-8, and then rolled back the BitReader.
   - Now, `peek_bytes(len)` inspects the underlying memory buffer with **zero heap allocations** and zero BitReader state mutation.
2. **Discriminator Regex Fast-Path:**
   - Discriminators checking `testPattern="."` or `testPattern="^."` now execute in $O(1)$ by directly testing `!self.reader.is_eof()` rather than dynamically invoking the regex engine.
3. **Avoidance of Full Infoset Tree Clones for XPath:**
   - The expression `{ ../count }` now resolves directly against parent stack frames via `find_sibling_in_parent`, eliminating the expensive cloning of entire XML infoset subtrees.

### Origin of the Remaining 2.15× Asymmetry (60.96 µs vs 28.35 µs)

The remaining gap between parsing (60.96 µs) and unparsing (28.35 µs) stems from structural differences inherent to DFDL runtime processing:

```
PARSER PIPELINE (60.96 µs):
Raw Bytes ──> [BitReader] ──> [Speculative Choice Dispatch] ──> [Schema Property Eval]
                                       │
                                       ▼
                       [Dynamic Infoset Tree Allocation] ──> Completed Infoset

UNPARSER PIPELINE (28.35 µs):
Pre-built Infoset ──> [Direct Tree Traversal] ──> [Binary Serialization] ──> Byte Sink
```

1. **Speculative Choice Resolution & Backtracking Checkpoints:**
   - Unparsing knows the exact element name and type directly from the input infoset node. It never speculates.
   - Parsing must evaluate choice branches, save checkpoints (`BitReader`, `InfosetBuilder`, `VariableMap`), and handle potential points of uncertainty (PoU).
2. **Heap Allocation of the Output Infoset:**
   - Parsing builds the complete XML/infoset DOM on the heap (`InfosetElement`, `QName`, `HashMap`, `Vec<InfosetNode>`).
   - Unparsing only traverses an already-allocated, read-only tree and serializes bytes directly into the output buffer.
3. **Dynamic Delimiter & Framing Verification:**
   - Parsing validates initiators, terminators, alignments, and skips byte-by-byte at each field boundary. Unparsing writes precomputed byte layouts.

## 3. Interpreted DFDL vs Native Rust Codec Comparison

| Scenario (192B Multi-Message File) | Interpreted DFDL | Native Rust Codec | Speedup Factor |
|:---|:---:|:---:|:---:|
| **Decode / Parse** | 60.96 µs | **49 ns** | **1,244.0× faster** |
| **Encode / Unparse** | 28.35 µs | **39 ns** | **726.9× faster** |
| **Full Roundtrip** | 91.12 µs | **94 ns** | **969.4× faster** |
| **Throughput** | 16,238 ops/s | **12,320,323 ops/s** | **758× higher** |
| **Data Bandwidth** | 2.97 MB/s | **2,255.92 MB/s (2.25 GB/s)** | **759× higher** |

### Architectural Insights for Mission-Critical Deployment

1. **Interpreted DFDL (61 µs):**
   - Ideal for dynamic schema loading, regulatory data interchange, mission replay, edge schema updates without recompilation, and general DFDL compliance (100% Daffodil TDML pass rate).
2. **Native Rust Codec (49 ns):**
   - Operates strictly in L1 cache with zero heap allocations, decoding 64-byte tactical track messages in **25 ns** and 192-byte track files in **49 ns**.
   - Suitable for real-time weapon systems, radar tracking loops (<1 ms budget), and high-frequency RF telemetry decoders.
3. **AOT Compiler Path (Future Work):**
   - Compiling DFDL IR ahead-of-time directly into native Rust bytecode/machine code bridges this gap, bringing interpreted DFDL schemas into sub-microsecond latency territory.
