## Technical Changes & Root Cause Analysis

### 1. DFDL §12.3.1 Table 33: LengthUnits and Binary Representation
- **Root Cause**: DFDL §12.3.1 specifies that if `dfdl:representation` is `'binary'` on simple elements, `dfdl:lengthUnits` can only be `'bytes'` or `'bits'`. `compiler.rs` previously did not enforce this error on simple types, causing `property_scoping_03` and `unparse_property_scoping_03` to not raise a schema definition error. Conversely, on complex types (`root9`), DFDL allows `lengthUnits="characters"` with appropriate character encoding.
- **Fix**: Added compile-time check in [compiler.rs](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-schema/src/compiler.rs) verifying that for simple elements, `representation == Binary` prohibits `lengthUnits == Characters`.
- **Impact**: `property_scoping_03`, `unparse_property_scoping_03`, and `pl_complexContentLengthCharacters_1` all pass 100%.

### 2. DFDL §12.3.4: Nested PrefixLengthType Validation
- **Root Cause**:
  - DFDL §12.3.4 allows prefix length types to have standard lengths.
  - Daffodil parser supports up to 1 level of nested prefix length type (`pl_text_string_pl_txt_bytes`), but rejects deeper nesting (`pl_nest_err` with depth > 1) at schema compile time.
  - Furthermore, Daffodil's unparser does not support nested prefixed lengths at all (`test_prefix_alignment_3`, `test_prefix_alignment_4`).
- **Fix**:
  - In [compiler.rs](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-schema/src/compiler.rs), inspected nested simple type's `lengthKind`. If `nested_len_kind == "prefixed"`, returned `Schema Definition Error: Nested dfdl:lengthKind="prefixed" is not supported`. For single nesting, embedded `@descriptor@` so parser can decode it while tracking nesting.
  - In [unparser.rs](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/kernel/unparser.rs), if `props.prefix_length_type` contains `@`, raised `Unparse Error: Nested dfdl:lengthKind='prefixed' is not supported`.
- **Impact**: `pl_nest_err`, `test_prefix_alignment_3`, `test_prefix_alignment_4`, and `pl_text_string_pl_txt_bytes` all pass 100%.

### 3. DFDL §13.7: HexBinary / Blob Unparse Length Bounds Check
- **Root Cause**: In [unparser.rs](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/kernel/unparser.rs), `DfdlValue::HexBinary(b)` wrote bytes to output before calculating or validating `target_bytes`. When unparsing a blob or hexBinary larger than the target explicit/implicit length, the excess data was written instead of returning an `Unparse Error: Blob length X bits exceeds Y bits`.
- **Fix**: Reordered unparse logic to evaluate `target_bytes` first; if `b.len() > target`, raise an `Unparse Error` with exact bit counts before writing.
- **Impact**: `blob_07` passes 100%.
