## Technical Analysis & Implementation Details

### 1. Issue 4: `Infoset document incomplete: no root element`
- **Root Cause**: [`InfosetBuilder::build()`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/infoset/tree.rs#L274-L288) previously emitted a hard `DFDLErrorKind::Parse` error when `doc.root` was `None` and the active element stack was empty.
- **Specification Context**: Per DFDL §14, when parsing terminates on empty streams or optional root occurrences with 0 elements matched, an empty `InfosetDocument` (`root: None, total_nodes: 0`) must be constructed rather than aborting with an incomplete document parse error.
- **Fix**: Updated [`InfosetBuilder::build()`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/infoset/tree.rs#L283) to return `Ok(InfosetDocument::new())` when both `self.doc.root` is `None` and `self.stack` is empty. This is consistent with `active_doc()`.

### 2. Issue 2: `Failed to parse text int scalar` & `dfdl:inputValueCalc` Resolution
- **Root Cause**:
  1. [`PropertyStore::to_resolved_properties()`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/expr/properties.rs#L302-L304) only retrieved `inputValueCalc` and `outputValueCalc` from local element property stores without checking the `parent` format/scope property store. When `inputValueCalc` was specified on format definitions or enclosing containers, `input_value_calc` resolved to `None`, forcing the parser to attempt a bitstream text integer read on unformatted/empty data streams.
  2. [`ParserEngine::parse_single_element_occurrence()`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/kernel/parser.rs#L462-L478) lacked coercions for evaluated expression results (`DfdlValue::Double`, `DfdlValue::Long`, `DfdlValue::String`, etc.) into target scalar simple types (`Int`, `Short`, `Byte`, `UnsignedInt`, `UnsignedShort`, `UnsignedByte`, `UnsignedLong`, `Float`, `Double`).
  3. [`SchemaCompiler::parse_schema_document_internal()`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-schema/src/compiler.rs#L104-L140) was missing support for top-level `<xs:complexType name="...">` declarations. When an element referenced a named complex type (`type="example1"`), `lower_element_to_ir()` emitted an empty sequence without child elements.
  4. [`TdmlRunner`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-tests/src/tdml.rs#L378-L384) now dynamically sets `schema.root_element_id` when test cases specify `root="..."`.
- **Specification Context**: Per DFDL §17.1, an element with `dfdl:inputValueCalc` does NOT consume any bits from the bitstream, and calculated values must be coerced into the element's target primitive type.
- **Fix**:
  - Added `named_complex_types` table to `XsdSchema` and parsed top-level `<xs:complexType name="...">` tags in `compiler.rs`.
  - Added `find_term_by_name()` on `CompiledSchema` and updated `TdmlRunner` to set `schema.root_element_id` for specified root elements.
  - Updated `inputValueCalc` and `outputValueCalc` property lookup in `properties.rs` to fallback to `parent.get_property(...)`.
  - Added comprehensive scalar coercions in `parse_single_element_occurrence` across all numeric primitive types and string parsing.

### 3. Issue 3: `Insufficient text data for explicit length scalar` & HexBinary Length Units
- **Root Cause**:
  In [`ParserEngine::parse_text_value()`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/kernel/parser.rs#L874-L880), character byte length calculation for `DfdlSimpleType::HexBinary` with `representation="text"` did not account for the 2:1 character-to-byte ratio when `lengthUnits="bytes"` or `lengthUnits="bits"`.
- **Specification Context**: Per DFDL §13.14 (`xs:hexBinary`), when `representation="text"` and `lengthUnits="bytes"`, `dfdl:length` represents the binary byte count, which corresponds to `2 * dfdl:length` text hex characters in the stream.
- **Fix**: Updated `parse_text_value()` to calculate `byte_len` as `l.saturating_mul(2)` for `DfdlSimpleType::HexBinary` when `lengthUnits == Bytes`, and `(l / 8).saturating_mul(2)` when `lengthUnits == Bits`.
