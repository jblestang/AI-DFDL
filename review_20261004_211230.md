## 1. Domain Expertise Analysis

### A. DFDL 1.0 Specification & Syntax Engineering
1. **Dynamic Separator Evaluation (DFDL §12.1):**
   - **Specification Clause:** Section 12.1 specifies that `dfdl:separator` is a List of DFDL String Literals or an expression evaluating to string literals. A separator cannot evaluate to an empty string or whitespace-only without entity escaping (`%SP;`, `%NL;`). Evaluating to an empty string at runtime MUST raise a Schema Definition Error: `"Schema Definition Error: Property separator cannot be empty string"`.
   - **Resolution:** Replaced silent fallback to `None` in `crates/dfdl-core/src/kernel/parser/mod.rs` with strict runtime schema definition error enforcement when `evaluated.trim().is_empty()`.
   - **Impact:** Resolved `dynSepAllWhitespace` in `dynamicSeparator.tdml`.

2. **Explicit Length String Unparsing & Padding Policy (DFDL §13.7.1):**
   - **Specification Clause:** Section 13.7.1 defines `dfdl:textPadKind` (`none`, `padChar`). When `textPadKind="none"`, no padding is performed; if the length of the data representation is less than the explicit length specified, an Unparse Error MUST occur.
   - **Resolution:** In `crates/dfdl-core/src/kernel/unparser.rs`, added strict checks in both character-based and byte/bit-based unparsing blocks. When `char_count < target_len` and `props.text_pad_kind == TextPadKind::None`, the engine rejects unparsing with an Unparse Error (`Data length X doesn't match expected output data length Y and textPadKind is 'none'`).
   - **Impact:** Resolved `negativeUnparseTest04` and `negativeUnparseTest04_ffb`.

3. **Bitstream Peeking Extension (`dfdlx:lookAhead`):**
   - **Specification / Extension Semantics:** `dfdlx:lookAhead(offset, bitsize)` requires inspecting `bitsize` bits starting at `offset` bits ahead of the current bit position without consuming stream data. If fewer bits remain than `offset + bitsize`, a Parse Error (`"Parse Error: Insufficient bits available"`) must be raised.
   - **Resolution:**
     - Extended [`BitReader`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/io/bitstream.rs) with `lookahead_bits(offset, num_bits) -> DFDLResult<u128>`. Used transactional `checkpoint()` / `rollback()` to guarantee bitstream position invariants under all outcomes.
     - Enabled multi-chunk 64-bit to 128-bit unsigned integer decoding for values exceeding primitive scalar operations (e.g. 65-bit lookaheads).
     - Connected lookahead via [`ExprContext::with_lookahead`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-core/src/expr/eval.rs) utilizing `core::cell::RefCell` to preserve strict `#![no_std]` compliance and closure reentrancy.
     - Preserved explicit `DFDLErrorKind::Parse` error kinds during `inputValueCalc` expression evaluation instead of flattening all failures into schema definition errors.
   - **Impact:** `lookAhead.tdml` achieved 100% pass rate (14/14 tests passing, resolving `lookAhead_tooFar_03` with 0 regressions on `lookAhead_06`).

4. **TDML Test Runner Evaluation Diagnostics:**
   - **Runner Behavior:** Unparser test cases in the official suite test both engine unparsing failures and the TDML runner's comparison engine (expecting TDML error messages when unparsed bytes differ from expected document bytes).
   - **Resolution:** In [`crates/dfdl-tests/src/tdml.rs`](file:///Users/jean-baptiste/AI-DFDL/crates/dfdl-tests/src/tdml.rs), when an unparser test expects error strings and unparsing succeeds but yields mismatched output bytes, formatted detailed diff messages (`"TDML Error: output data length ... doesn't match expected length ..."`) and matched them against `tc.expected_errors`.
   - **Impact:** Resolved all remaining negative unparse runner tests in `testUnparserGeneral.tdml` and `testUnparserFileBuffering.tdml`.
