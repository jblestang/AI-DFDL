## 2. Root Cause Analysis & Standard-Conforming Architectural Fixes

### A. Number Formatting: Preservation of Intra-Digit Whitespace (DFDL §13.7.1 & ICU Lax DecimalFormat)
- **Defect:** `sanitize_numeric_string` previously performed `clean.retain(|c| !c.is_ascii_whitespace())`. This stripped intra-digit whitespace indiscriminately, causing invalid numeric inputs like `"9 99"` or `"99 9"` to succeed when parsing `xs:int`, `xs:short`, `xs:byte`, etc., violating both XML Schema lexical representation rules and DFDL `textNumberCheckPolicy="lax"`.
- **Architectural Fix:** Replaced indiscriminate whitespace deletion with strict boundary trimming: leading and trailing whitespace is stripped, and whitespace immediately following recognized currency prefixes (`$`, `€`, `£`, `#`) is trimmed per ICU lax parsing rules. Intra-digit whitespace is strictly preserved, ensuring that invalid number syntax is properly rejected across all DFDL numeric types.
- **Standards Reference:** DFDL v1.0 §13.7.1, XML Schema Part 2 §3.2.3.

### B. ISO 8601 Calendar Formatting: Rejection of Prohibited `-00:00` and Named Timezones (XML Schema 1.0 §3.2.7 & DFDL §13.11.1)
- **Defect:** `DateTime` and `Time` previously permitted timezone `-00:00` under `calendarCheckPolicy="lax"`, and `normalize_timezone_suffix` improperly coerced `-00:00` to `+00:00`.
- **Architectural Fix:** Under XML Schema 1.0 §3.2.7, `-00:00` is explicitly prohibited and illegal for all XML Schema datetime types. Under `calendarPatternKind="implicit"`, ISO 8601 formatting requires either `Z` or `(+|-)HH:mm`. Timezone `-00:00` is now unconditionally rejected for `xs:dateTime`, `xs:date`, and `xs:time`.
- **Standards Reference:** XML Schema 1.0 Part 2 §3.2.7, DFDL v1.0 §13.11.1.

### C. Simple Type Default Property Inheritance Across Schema Inclusions (DFDL §5.2.1 & DFDL Extensions)
- **Defect:** When compiling schema inclusions with different target namespaces or document-level defaults, named simple types in included documents discarded their document's `dfdl:format` defaults upon AST merge. When a schema defined a binary representation type (e.g. `<dfdl:format representation="binary"/>`), the importing schema compiled it with `representation="text"`, causing parsing failure on binary bytes.
- **Architectural Fix:** In `XsdSchema::merge`, default properties from `other.global_format` are merged into `other.named_simple_types` prior to incorporation into the root schema's AST.
- **Standards Reference:** DFDL v1.0 §5.2.1 (Scope of DFDL Properties).

### D. Separation of Mandatory Text Alignment from Binary Representation (DFDL §13.2.1)
- **Defect:** In `parse_single_element_occurrence`, mandatory text alignment (MTA) was being invoked whenever `elem.type_ir == CompiledType::Simple(DfdlSimpleType::String)` even if `term.properties.representation == Representation::Binary` or the element utilized `dfdlx:repType`. In `enums.tdml` (`repTypeAlignment`), an 8-bit stream containing 8 1-bit binary enum elements was being prematurely exhausted because MTA rounded bit offsets up to 8-bit byte boundaries after every 1-bit read.
- **Architectural Fix:** Enforced DFDL §13.2.1: Mandatory text alignment only applies to elements whose effective representation is `Representation::Text` and which do not use representation types (`rep_type.is_none() && rep_simple_type.is_none()`). Furthermore, `compiler.rs` now inherits `length_units`, `alignment`, and `alignment_units` from `rep_props` when defined on a `dfdlx:repType`.
- **Standards Reference:** DFDL v1.0 §13.2.1, DFDL Extensions §4.

### E. Universal Multi-Byte Little-Endian Integer Swapping (DFDL §13.7.1.4)
- **Defect:** `read_binary_bits` and unparser binary integer emission previously assumed LittleEndian integers were either 16, 32, or 64 bits based on primitive enum variants. When an element like `<element name="w" type="xs:int" dfdl:length="16"/>` had an explicit non-standard length with `byteOrder="littleEndian"`, `u32.swap_bytes()` was executed on 32 bits instead of reversing the actual 16-bit payload, zeroing out valid data.
- **Architectural Fix:** Implemented `order_integer_bytes(val: u64, bits: usize, byte_order: ByteOrder) -> u64` in `crates/dfdl-core/src/util.rs`. It symmetrically reorders any integer between 1 and 8 bytes (`bits / 8`) using checked/saturating bit arithmetic, ensuring correct LittleEndian and BigEndian handling across both parser and unparser for any arbitrary bit width.
- **Standards Reference:** DFDL v1.0 §13.7.1.4.
