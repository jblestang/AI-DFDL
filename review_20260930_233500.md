## 2. Root Cause Analysis & Standards Mapping

### 2.1 Bit-Level Length Slicing for `xs:hexBinary` and `xs:string` (DFDL 1.0 §12.3.7, §13.8)
- **Failure Mechanism:** When an element specified `dfdl:lengthUnits="bits"` with a length that is not a multiple of 8 (e.g., `length="13"`, `length="5"`, `length="22"`, `length="3"` in `SimpleTypes.tdml`), `parse_binary_value` computed `len = explicit_len.div_ceil(8)` and executed `for _ in 0..len { self.read_binary_bits(8)? }`. This consumed whole 8-bit bytes for every iteration, reading beyond the element's explicit bit length and starving subsequent adjacent bit-level fields of data, triggering `Insufficient binary data for primitive scalar`.
- **Standards Requirement (DFDL 1.0 §13.8 & §12.3.7.2):** An element with `lengthUnits="bits"` must consume exactly the specified bit count. When mapped to bytes for `xs:hexBinary`:
  - In `MostSignificantBitFirst` (MSBF), partial bytes place the bits left-aligned (`val << (8 - chunk)`), zero-padded at the least significant bits.
  - In `LeastSignificantBitFirst` (LSBF), partial bytes place the bits right-aligned (unmodified), zero-padded at the most significant bits.
- **Implementation:** Replaced byte-by-byte iteration with bit-by-bit chunk extraction (`chunk = bits_left.min(8)`), reading exact bit counts (`self.read_binary_bits(chunk)`), padding partial chunks per active `bitOrder`, and advancing the reader by only the exact requested bit count.

### 2.2 Complex Element Explicit Length Skipping & Bounds (DFDL 1.0 §12.3.3)
- **Failure Mechanism:** Complex elements declaring `dfdl:lengthKind="explicit"` (such as `<xs:element name="data" dfdl:length="208" dfdl:lengthKind="explicit">` in `ISRM_green_to_orange_60000.dfdl.xsd`) evaluated `_complex_len` but discarded the result. If a choice branch inside the complex element consumed fewer bytes than the explicit container length (e.g. `IsrmEnd` sequence consuming 0 bytes instead of 208 bytes), the parser failed to advance to the end of the container, causing subsequent sibling records to be read at misaligned byte offsets.
- **Standards Requirement (DFDL 1.0 §12.3.3):** The representation of an explicit-length complex element begins at the start of its first child and ends when the specified length is reached. If children consume less than the specified length, remaining bits are skipped. If children exceed the specified length, a processing error must be raised.
- **Implementation:** Added `skip_bits(&mut self, bits: usize)` to `BitReader`. In `CompiledType::Complex`, calculated `expected_bits` from `complex_len` and `length_units`. If `current_bit < target_bit`, skipped remaining bits to position the stream precisely at `target_bit`. If `current_bit > target_bit`, raised a parse error.

### 2.3 Prefix Length Type Resolution (`dfdl:lengthKind="prefixed"`, DFDL 1.0 §12.3.4)
- **Failure Mechanism:** `compiler.rs` previously replaced any custom simple type reference in `prefixLengthType` with `"xs:unsignedShort"` whenever the base type was not an explicit primitive integer. For instance, `threeByteBinInt` (3 bytes = 24 bits) and `twentyFourBitsBinInt` were overridden to 16-bit `unsignedShort`, causing prefix length reads to under-consume 8 bits and misalign the entire subsequent element payload.
- **Standards Requirement (DFDL 1.0 §12.3.4):** `dfdl:prefixLengthType` specifies a simple type whose DFDL properties dictate the physical representation, length, and units of the length prefix.
- **Implementation:**
  - Preserved the clean simple type identifier in `compiler.rs` when base types are extended integers.
  - In `parser.rs`, implemented 24-bit integer bit-swap for little-endian ordering (`(b0 << 16) | (b1 << 8) | b2`), recognized 24-bit (`twentyfour` / `threebyte`) and 8-bit (`prefixlengthtype`) naming, and added support for textual prefix lengths (`twentyFourBitsTextInt`, `threeCharTextInt`).

### 2.4 Binary Calendar Representation (`dfdl:binaryCalendarRep`, DFDL 1.0 §13.11)
- **Failure Mechanism:** `DfdlSimpleType::DateTime`, `Date`, and `Time` elements with `dfdl:representation="binary"` and `dfdl:lengthKind="implicit"` defaulted to 8 bytes, causing underflow on 4-byte `binarySeconds` representations (e.g. `dateTimeBin4`).
- **Standards Requirement (DFDL 1.0 §13.11):** For binary calendar types, `binarySeconds` occupies 4 bytes (32 bits), whereas `binaryMilliseconds` occupies 8 bytes (64 bits).
- **Implementation:** Added `BinaryCalendarRep` enum to `dfdl-core::schema::ir`, parsed `dfdl:binaryCalendarRep` in `properties.rs`, and mapped implicit binary calendar lengths to 4 bytes for `BinarySeconds` and 8 bytes for `BinaryMilliseconds`.

### 2.5 External File Loading in TDML Test Runner (`type="file"`)
- **Failure Mechanism:** TDML documents using external test files (`<tdml:documentPart type="file">` and `<tdml:dfdlInfoset type="file">`) were previously loaded as empty byte vectors, causing tests to starve on input data.
- **Implementation:** Added `assemble_document_bytes_with_base_dir` and external file resolution against `base_dir` in `TdmlRunner`.
